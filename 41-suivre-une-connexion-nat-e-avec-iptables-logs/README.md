# Suivre une connexion NATée avec iptables logs

**Rappel théorique** Le NAT (Network Address Translation) est le mécanisme par lequel un routeur ou un pare-feu modifie l'adresse source ou destination d'un paquet IP au passage. Dans le cas le plus courant (SNAT/masquerade), une machine du réseau privé (ex. 192.168.1.10) émet une requête vers Internet ; le pare-feu remplace l'IP source privée par son IP publique avant de faire suivre le paquet. Quand la réponse arrive, le pare-feu effectue l'opération inverse (DNAT) et redirige le paquet vers la machine d'origine. Ce suivi est possible grâce au module conntrack du noyau Linux, qui maintient une table d'état des connexions actives. Sous iptables, les logs sont générés via la cible LOG, placée dans les chaînes INPUT, OUTPUT, FORWARD ou dans les tables nat (PREROUTING, POSTROUTING). Un log iptables type ressemble à : [timestamp] IN=eth0 OUT=eth1 SRC=192.168.1.10 DST=8.8.8.8 PROTO=TCP SPT=54321 DPT=443. Le champ SRC avant NAT diffère du SRC visible côté Internet : c'est précisément cette transformation qu'il faut être capable de tracer. Erreurs fréquentes : confondre la chaîne PREROUTING (avant décision de routage) et POSTROUTING (après décision de routage) ; oublier que les logs dans la table nat ne capturent que le premier paquet d'une connexion (conntrack optimise les suivants) ; ne pas préciser de préfixe de log, rendant le tri dans syslog très difficile. Mini-exemple : pour logger tout trafic sortant avant masquerade, on utilise : iptables -t nat -A POSTROUTING -j LOG --log-prefix "NAT-POST: " --log-level 4 --- **Énoncé de l'atelier** Dans ce workshop, vous allez mettre en place...
