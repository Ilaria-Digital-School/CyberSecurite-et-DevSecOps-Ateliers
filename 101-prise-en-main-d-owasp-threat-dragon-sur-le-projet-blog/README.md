# Prise en main d’OWASP Threat Dragon sur le projet Blog

RAPPEL THÉORIQUE La modélisation des menaces consiste à identifier, de manière structurée, ce qui peut mal tourner dans une application avant qu’un attaquant ne le fasse. Le mental model à retenir : on décrit d’abord le système (composants, flux de données, frontières de confiance), puis on cherche systématiquement les menaces à l’aide d’une méthode comme STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege). Chaque menace identifiée est ensuite évaluée (Risk Rating) et traduite en mesures de mitigation ou en tests. OWASP Threat Dragon est un outil open source qui permet de dessiner un Data Flow Diagram (DFD) et d’attacher des menaces STRIDE à chaque élément (processus, magasin de données, acteur externe, flux). L’élément clé du DFD est la Trust Boundary : c’est la ligne qui sépare deux zones de niveaux de confiance différents (ex. Internet ↔ serveur, serveur ↔ base de données). C’est là que se concentrent la majorité des menaces. Erreurs fréquentes : dessiner une architecture technique au lieu d’un flux de données, oublier les frontières de confiance, lister des menaces génériques non contextualisées, ou confondre menace (ce qui peut arriver) et vulnérabilité (la faille précise). Mini-exemple : sur un flux « Navigateur → API /login », un Tampering possible est la modification du corps de la requête, mitigé par validation serveur + HTTPS. ÉNONCÉ DU WORKSHOP Vous allez modéliser les menaces du projet « Blog », une application web classique composée d’un frontend, d’une API backend, d’une base de données et d’un mécanisme d’authentification...
