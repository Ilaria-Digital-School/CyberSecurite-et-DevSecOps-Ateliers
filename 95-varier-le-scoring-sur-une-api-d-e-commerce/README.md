# Varier le scoring sur une API d’e-commerce

RAPPEL THÉORIQUE Le scoring d'une menace consiste à lui attribuer une note de risque afin de prioriser les corrections et les tests. Dans les activités précédentes, vous avez utilisé la méthodologie OWASP Risk Rating, qui décompose le risque en deux dimensions : la probabilité (likelihood) et l'impact. La probabilité agrège des facteurs liés à l'attaquant (compétence, motivation, opportunité) et à la vulnérabilité (facilité de découverte, d'exploitation, notoriété, détection d'intrusion). L'impact agrège des facteurs techniques (perte de confidentialité, d'intégrité, de disponibilité, de traçabilité) et métier (dommage financier, réputation, non-conformité, atteinte à la vie privée). Le score final = Probabilité × Impact, classé en Faible / Moyen / Élevé / Critique. Le mental model à retenir : un même identifiant de menace peut recevoir des scores très différents selon le contexte métier et l'audience du scoring (technique vs direction). Une injection SQL sur une route d'administration n'a pas le même impact que sur un endpoint public de recherche. Erreurs fréquentes : confondre CVSS et OWASP Risk Rating, négliger totalement l'impact métier au profit du seul impact technique, ou encore appliquer un scoring 'moyenné' qui lisse les risques critiques. Autre piège : oublier que le contexte de déploiement (données de paiement, RGPD) fait varier l'impact métier. Mini-exemple : un CSRF sur '/cart/add' est souvent Faible en impact métier, alors qu'un CSRF sur '/account/email' facilitant une prise de contrôle de compte grimpe en Élevé. --- ÉNONCÉ DU WORKSHOP Vous êtes mandaté comme analyste sécurité junior sur une API REST d'e-commerce fictive nommée ShopAPI.
