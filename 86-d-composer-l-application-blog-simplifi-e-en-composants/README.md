# Décomposer l’application Blog simplifiée en composants

RAPPEL THÉORIQUE Avant de modéliser des menaces sur une application, il faut d'abord comprendre sa structure. La décomposition consiste à découper une application en composants élémentaires : interfaces utilisateur, services applicatifs, bases de données, API, systèmes d'authentification, stockage de fichiers, dépendances externes. Le mental model à retenir est simple : "on ne protège bien que ce que l'on comprend". Chaque composant manipule des actifs (données, fonctionnalités) et communique avec d'autres via des flux de données. Ces flux traversent parfois des frontières de confiance (trust boundaries) : le passage d'une zone où l'on fait confiance à une autre où l'on ne fait pas confiance, par exemple entre le navigateur de l'internaute et le serveur. Ce travail prolonge directement ce que vous avez déjà vu : identifier les actifs (Todo List), raisonner en CIA (Confidentialité, Intégrité, Disponibilité), distinguer Actor et Attacker, puis relier les scénarios à l'OWASP Top 10. Ici, vous appliquez ces notions à une nouvelle application : un blog. Erreurs fréquentes : confondre un composant avec une simple fonctionnalité, oublier les composants invisibles (base de données, cache, service d'authentification), ou ne pas identifier les frontières de confiance. Autre erreur classique : lister les composants sans décrire les flux entre eux. Mini-exemple : dans une Todo List, le composant "API Todo" reçoit une requête du "Frontend Web" (flux HTTPS traversant une frontière de confiance), consulte la "Base de données" (flux interne), et renvoie la liste. Trois composants, deux flux, une frontière. Voilà exactement ce que vous allez produire pour le blog....
