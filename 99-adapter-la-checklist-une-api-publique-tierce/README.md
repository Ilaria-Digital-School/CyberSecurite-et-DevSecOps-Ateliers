# Adapter la checklist à une API publique tierce

RAPPEL THÉORIQUE Une checklist de tests de sécurité est un outil dérivé de votre modélisation des menaces (STRIDE) et de votre priorisation par OWASP Risk Rating. Elle liste, pour chaque menace identifiée, les tests concrets à exécuter afin de valider ou d'infirmer l'existence d'une vulnérabilité. Le mental model à retenir est simple : une checklist n'est jamais universelle, elle épouse la surface d'attaque du système ciblé. Or, une API publique tierce (une API que vous consommez mais que vous ne développez pas et ne contrôlez pas, comme celle de Stripe, GitHub ou une API météo) change radicalement la donne par rapport à une API interne. Vous n'avez ni le code source, ni le droit de la scanner agressivement, ni la maîtrise de son authentification. Les erreurs fréquentes : (1) copier-coller une checklist d'API interne sans retirer les tests hors périmètre (ex. injection SQL directe sur un backend que vous ne possédez pas) ; (2) oublier que la surface d'attaque réelle se déplace vers l'intégration — la façon dont VOTRE application manipule les clés, les tokens, les réponses et les erreurs de l'API tierce ; (3) ignorer les aspects légaux et contractuels (Terms of Service, rate limiting, tests non autorisés). Mini-exemple : la menace STRIDE « Information Disclosure » sur une API tierce ne se teste plus en cherchant une fuite dans SON code, mais en vérifiant que VOTRE application ne logge pas les clés API, ne les expose pas côté client, et gère correctement les données sensibles renvoyées par l'API....
