# Repérer les actifs dans une application "Todo List"

RAPPEL THÉORIQUE Avant de tester ou de sécuriser une application, il faut savoir ce qu'on protège. C'est le rôle de l'identification des actifs (assets). Un actif est tout élément ayant de la valeur pour l'organisation ou l'utilisateur : données (mots de passe, tokens, contenu privé), fonctionnalités critiques (authentification, gestion des droits), composants techniques (base de données, API, serveur) ou éléments intangibles (réputation, conformité RGPD). Rappelez-vous la chaîne vue précédemment : un actif possède des vulnérabilités, qu'une menace peut exploiter, générant un risque. Le bon mental model consiste à se poser trois questions face à chaque partie de l'application : « Qu'est-ce qui a de la valeur ? », « Pour qui ? » et « Que se passe-t-il si c'est compromis (perte de confidentialité, d'intégrité ou de disponibilité) ? ». Cette approche CIA (Confidentiality, Integrity, Availability) structure votre analyse. Erreurs fréquentes : (1) confondre actif et vulnérabilité — le mot de passe est un actif, son stockage en clair est une vulnérabilité ; (2) ne lister que les données visibles en oubliant les actifs techniques (jetons de session, clés API, logs) ; (3) ignorer les actifs métier (disponibilité du service, confiance des utilisateurs). Mini-exemple : dans une messagerie, les actifs incluent le contenu des messages (confidentialité), l'identité du compte (intégrité de l'authentification), et le service lui-même (disponibilité). Chacun mérite une évaluation distincte de son importance.
